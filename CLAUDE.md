# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SkyCareer is a standalone Windows career add-on for Microsoft Flight Simulator 2024 (C# / .NET 10, WPF host with Blazor Hybrid UI and MudBlazor 9). The UI is English (default) and German; code, identifiers, comments, logs, README, CHANGELOG and release notes are English (see Localization below).
Always use aviation related terminology where appropriate.

## Commands

```bash
dotnet build SkyCareer.sln
dotnet test SkyCareer.sln
dotnet test tests/SkyCareer.Sim.Tests --filter "FullyQualifiedName~FlightTrackingTests.Touchdown_reports_rate_and_peak_g"
dotnet run --project src/SkyCareer.App
dotnet tool restore
dotnet ef migrations add <Name> --project src/SkyCareer.Data -o Migrations
```

- A running `SkyCareer.App.exe` locks `src/SkyCareer.App/bin/...`; close it first, or build the app elsewhere with `dotnet build src/SkyCareer.App -o <tempdir>`.
- The app migrates the database on startup. The DB lives at `%LOCALAPPDATA%\SkyCareer\skycareer.db` (override with the `SKYCAREER_DB` env var, e.g. to test the UI against a throwaway DB without touching the user's careers), user content in `Documents\SkyCareer\content`, exported flight plans in `Documents\SkyCareer\Flugplaene`.

## Localization

- `src/SkyCareer.Localization` (lowest layer, referenced via Domain): `L.T("English text")`, `L.F("English {0}", x)` (in Razor `@T(...)`/`@F(...)` via `@using static SkyCareer.Localization.L` in `_Imports.razor`), `L.Eur(amount)`. The English source text is the key; German lives in embedded `de/*.json` dictionaries (one per area: `core`, `engine` = libraries, `flight` = market/flight/fleet pages, `app` = other pages and services), merged at load. A missing translation falls back to English.
- Every user-visible text goes through `T`/`F` with a **literal** key, and needs a German entry with the same placeholders: `TranslationCoverageTests` scans `src/**/*.cs|razor` for the literals and fails on missing/orphaned entries or placeholder mismatches. Data (names, ICAO codes) is not translated.
- Mission types: English `name`/`description` in `content/missions/*.json` plus `"texts": { "de": { "name", "description" } }`; show `MissionType.DisplayName`/`DisplayDescription`.
- `AppSettings.Language` (null = Windows display language via `L.SystemLanguage`) is applied by `L.SetLanguage` at startup before anything else; it sets the default thread cultures, so number/date formats and background threads (settlement, automation) follow. `LanguageSelect.razor` (Settings, career selection) switches and reloads the UI. Stored texts (ledger descriptions, flight notes, unavailability reasons) keep the language they were created in.
- `AppLog` file logs are English and not translated. Test projects run in English (module initializer).

## SimConnect is optional at build time

`SkyCareer.Sim.csproj` compiles the real `SimConnectSource` only when the MSFS 2024 SDK is found (via `SimConnectSdkDir`, the `MSFS2024_SDK` env var, or the default `C:\MSFS 2024 SDK`). It then defines `HAS_SIMCONNECT`, references the managed wrapper, copies the native `SimConnect.dll`, and targets x64. Without the SDK everything still builds and the app works in replay mode. Code outside `SimConnect/SimConnectSource.cs` must not reference SimConnect types; go through `FlightDataSourceFactory` and the interfaces in `Telemetry.cs` / `AircraftInspection.cs` (`IFlightDataSource`, `IAircraftLoader`, `IAircraftInspector`).

SimConnect facts verified against the live sim (keep them in mind when changing `SimConnectSource`):
- L:Vars can be read directly in data definitions, but **unknown L:Vars return 0 instead of an error**. Detect add-ons by plausible values, not by success (see `GsxState.Detected`).
- `DESIGN SPEED VC` already returns cruise **TAS** (525 kt for the Citation X).
- One-shot reads go through `RequestOnceAsync`, which maps SimConnect exceptions back to the request by packet id. Batch reads use a fixed 16-double struct (`ReadVariablesAsync`), padded with dummy L:Vars.
- Optional variables (`ReadDesignAsync`) sit in a separate request so a missing variable doesn't break the whole snapshot.
- Airport facility data (`ReadAirportAsync`): ILS is detected from **approaches of type 4 (ILS)**. The runway `PRIMARY/SECONDARY_ILS_ICAO` fields are empty at some airports (LSZH) and only serve as extra info. Read char[8] idents as byte arrays (string marshaling produced garbage). Unknown idents answer with an exception and no end record. Results are cached in the `AirportFacilities` table; OurAirports has no ILS data (`navaids.csv` only covers VOR/NDB/DME/TACAN).

## Architecture

Dependency direction: `Domain` ← `Sim`, `Missions`, `Data`, `Integrations.*` ← `Application` ← `App`. `Domain` has no external dependencies.

- **Domain**: units (`Mass` in kg, SimConnect pounds converted at the edge; `Money` as decimal), aircraft profiles, load planning (`LoadSheetBuilder`, `FuelPlanner`, `LoadVerifier`), the finance cost model, career entities (`Career`, `FleetAircraft`, `MissionContract`, `FlightRecord`, `LedgerEntry`), and the simulator-independent `FlightResult`.
  - Crew convention: `OperatingEmptyKg` equals the sim's EMPTY WEIGHT. Crew is loaded into crew stations on top, unless `CrewIncludedInEmptyWeight`; cabin crew without crew seats of their own (crew stations' seats < pilots + cabin crew, e.g. the Citation X with only PILOT/COPILOT) go to the hold stations instead, with `StationLoad.CrewMass` marking that share so `GsxLoadSync.ScaleStations` keeps it aboard (before, the pilots weighed 270 lb). `LoadSheet.SimPayload` (payload + crew) is what the sim should report. Crew mass and crew costs use `AircraftProfile.Pilots` = max(`CrewCount`, `MinimumPilots`): two pilots for jets, MTOW > 5.7 t or > 9 seats unless tagged `single_pilot`. Pilots count `CrewMassKg` (default 85 kg), cabin crew `CabinCrewMassKg` (default 75 kg, EASA standard masses); SimBrief's airframe OEW is assumed to contain the pilots but not the cabin crew, so `SimBriefPayload` never sends pilots and always adds the cabin crew's standard mass to `cargo` (see SimBrief facts).
- **Sim**: `FlightSession` combines `FlightPhaseTracker` (phase state machine with hysteresis, touchdown/bounce detection) and `IntegrityMonitor` (slew, sim rate, refuelling in flight, payload change, teleport, aircraft change). `Arrived` needs the aircraft stationary on the ground with all engines off, confirmed after 5 s with the parking brake or after `ParkedWithoutBrakeConfirm` (30 s) without: add-ons like the Fenix A320/A321 drive their own brake logic and never set `BRAKE PARKING POSITION` (it reads true only briefly while the aircraft loads). Payload is locked when the takeoff roll starts (released again after a rejected takeoff) and only checked from `TakeoffRoll` to `Approach` (unloading after landing is fine). After an app restart `FlightSession.ContinueAfterRestart` (journal replay) bridges a gap > 30 s without judging it: a different payload becomes the new lock (noted), a landing in the gap continues on the ground via `FlightPhaseTracker.Resume` without a touchdown rating. Violations never void a job: `FlightSettlement.ViolationPenalties` deducts per kind (slew/teleport/aircraft change 20 %, refuelling in flight 15 %, payload change 10 %, capped at 20 % of the payout), −1 reputation per kind and 20 safety score points; time acceleration is only noted (no payout, score or reputation cost). `FlightOutcome.Failed` only remains for old records. `ReplaySource` and `FlightLogFile` (JSON Lines) make all tracking testable without MSFS; tests build telemetry with `SyntheticFlight`.
- **Missions**: data-driven content. `ContentLoader` layers content roots (a later root overrides by id). `ContentStore` holds the current `GameContent` (shipped `content/` plus the user folder) and reloads after edits. Mission types are JSON (`content/missions`); the `RequirementEvaluator` matches them to aircraft via tags/seats/cargo/surfaces/range. `IMissionGenerator` implementations are selected by the mission type's `generator` name. `StandardMissionGenerator` only offers jobs whose load sheet fits the limits, weights destinations log-normally around 45 % of the aircraft's range (divided by distance^1.5 so the many far-away airports don't crowd out medium trips), and honours an optional `MissionSearch` (also used as the market list filter). `PaxRule.LoadFactor`/`LoadFactorSpread` make the seated count lean towards a full cabin (normal around the mean, relative to `StandardMissionGenerator.Capacity` = min(type max, seats, search max)); without it the draw is uniform. `MissionType.ReturnFlight` (`chance`, `bonus`) adds a return leg B→A to some offers (`MissionOffer.Return`, own load and deadline after the outbound's plus turnaround). `Settlement/FlightSettlement` is a pure function: contract + `FlightResult` → outcome, score, ledger lines, wear, reputation.
- **Data**: one SQLite DB for all careers (scoped by `CareerId`, FK cascade) plus shared airport data from OurAirports (`OurAirportsImporter`). At import each airport is matched to the city it serves (`GeoNamesCities`, GeoNames cities15000: population fading with distance, capital flag); mission types weight destinations by that via `destinations.cityWeight` and can demand a per-search `minCapitalShare` (enforced in `SearchMarketAsync` like `minLargeShare`, via `RequireCapital`); `distanceInfluence` (< 1) damps the preferred-distance weighting so city importance wins. Military fields are flagged by name at import (`OurAirportsImporter.IsMilitaryField`, joint-use fields with scheduled service stay civil) and only offered to profiles tagged `military`. By convention, enums and `decimal` are stored as strings, so sums and money sorting happen in memory.
- **Application**: `CareerService` is the only place career state changes (fleet incl. relocation by paid ferry flight via `CostModel.Ferry` or free move, market, accept/start/complete flight, wait, monthly fixed costs). Mission pay (`StandardMissionGenerator.Payout`) = rule terms (incl. `perPaxNm` per seated passenger and nm) + `pay.hourlyRateFactor` × `FleetEconomics.HourlyRate` (rent + fuel per block hour) × (1 − `occupancyShare` + `occupancyShare` × seat occupancy), so payouts follow the aircraft class and how full the cabin is; `StandardMissionGenerator.TryBuild` then multiplies by `ReputationFactor` (1 + `MaxReputationBonus` 0.5 × reputation/100, from `GenerationContext.Reputation`), fixed in the offer. Packages: legs share `MissionContract.PackageId`, numbered by `PackageLeg` 1…`PackageLegs`, of a `PackageKind` (`Return`, `MultiStop`, `Delivery`, `Story`; null fields on packages from before 0.6 mean a two-leg `Return`) with `PackageBonusShare` (null = the type's `ReturnFlight.Bonus`). The generator returns `MissionOffer.FollowUps` (round trip via `ReturnFlight`, runs via `MissionType.MultiStop`: 2–4 legs within `minLegNm`/`maxLegNm`, no stop twice, optional `returnToOrigin`, `sameLoad` for roadshows (VIP, charter: every leg carries leg 1's passengers, bags and cargo via `BuildWithLoad`, never trimmed, the run is dropped when a leg exceeds a limit); the first stop honours the search and `RequireLarge`/`RequireCapital`; each leg starts after the previous deadline + `LegTurnaround`), and `CareerService.AddFollowUps` stores them with consecutive flight numbers. Later legs (`IsFollowUpLeg`) are only accepted with leg 1 (`AcceptAsync`), kept on the market while leg 1 is (`DropOffersAwayFromAsync`, the cap removes packages whole), cancelling a leg cancels the later ones, and the last leg's settlement adds `SettlementInput.PackageBonus` (share × all payouts) when every earlier leg ended `Completed`. Each leg arms on its own once the aircraft is at its origin. The market is reproducible: `SearchMarketAsync` (without the tests' `rng`) draws each aircraft's offers from a stream keyed by `Career.MarketSeed` (random at creation or entered on the career screen; careers from before 0.3 derive it from their id via `CareerService.MarketSeedOf` and store it at the first search), the game date (`d-M-yyyy`), location, registration and `MissionSearch.Fingerprint` (`CareerService.MarketStream`, hashed with `Domain/StableHash`); every attempt gets `new Random(StableHash.Of(stream, index))`, offers store `MissionContract.MarketStream`/`MarketIndex`, and a repeated search continues after the highest index, so restarts and copies of a career see the same jobs (changed content, airport data or learned ILS data change them). A search adds `OffersPerSearch` (60) offers per aircraft, `MaxOffersPerAircraft` (240) are kept; the market page shows 50 per page. At most `MaxOffersPerDestination` (10) open first legs of one type go to one destination per aircraft (`GenerationContext.DestinationFull`, counted from the stored offers plus the search's new ones), and destinations without any offer weigh ×2 (`Unserved`). `MissionSearch`: `PayPerHourMin` (payout ÷ `BlockHours`, checked by the generator and, for whole packages, by the market list) and `KnownToSimOnly` (`Airport.KnownToSim`); there is no ILS filter any more (the fingerprint keeps a fixed `False` in its place, and criteria added later only append to it when set, so older market streams stay the same). The market filter's client/story/package/demand options filter the list only (`MarketFilter.MatchesKind`). The map draws routes only for accepted jobs and the selected offer (`Route.Selected`); other offers are destination pins. Airline profile (`Airline.razor`, `/airline`, second menu entry): `Career.AirlineIcao`/`AirlineTelephony` (null = derived from the name by `Domain/Career/AirlineCodes`: initials of distinctive words, then generic ones like "Air", filled with consonants; `CareerService.AirlineIcaoOf`/`AirlineTelephonyOf`), pilot name and home base (`UpdateAirlineAsync`; the base only applies to new aircraft) and key figures (`GetAirlineOverviewAsync`); the career details moved there from Settings. Flight numbers are set at generation (`MissionContract.FlightNumber`, copied to `FlightRecord.FlightNumber`): scheduled jobs (category `airline`) one odd number per route from `StableHash(seed, origin, destination)`, others odd 1000–9999 from the attempt's `Random`, return legs +1; `FlightNumberOf` gives older jobs a stable one. "Plan in SimBrief" sends `airline`, `fltnum` and `callsign` (ICAO + number). The market filter (`App/Services/MarketFilter`) is stored per career as `Career.MarketFilterJson` (`SaveMarketFilterAsync`, no `Changed`) on every change and loaded when the page opens for another career. Each method uses its own `DbContext` from `IDbContextFactory` and raises `Changed`. Game time is flight-based: it only advances through flights (+ turnaround) and `WaitAsync`.
- **Integrations**: `SimBrief` (dispatch link + OFP fetch/validation, no API key), `Gsx` (reads `FSDT_GSX_*` L:Vars; `GsxLoadSync` turns GSX boarding/deboarding progress into scaled station loads and sets the load sheet's block fuel after GSX refuelling or boarding only when nobody else fuelled (a GSX refuelling that raised the fuel, EFB uplift or restored fuel is kept) and only after seeing the service run, since GSX can show a stale `Completed` at sim start; `GsxReceiptReader` reads GSX Pro's receipts; `GsxClient.ServiceVariables` reads cleaning/water/lavatory states in a second batch (the first holds 14 of 16 variables; the names `L:FSDT_GSX_CLEANING_STATE`/`WATER_STATE`/`LAVATORY_STATE` are unverified, unknown L:Vars read 0); `GsxServiceWatch` counts catering, cleaning, water and lavatory once seen requested/performing for the tracked job and then completed or no longer running (a stale `Completed` at sim start doesn't count); `GsxCoordinator.PreDepartureServices` feeds `FlightAutomation.PreDepartureServices`, stored at liftoff as `MissionContract.GroundServices`; `FlightSettlement.GroundServiceBonus` adds +1 reputation each, at most +2, on completed/late passenger flights), `BeyondAtc` (BeyondATC has no API; `PlnExporter` writes MSFS `.pln` files it can import; MSFS only loads plans whose departure and destination are airports it knows (a user waypoint as destination fails, verified 2026-11-08), so an airport with `Airport.KnownToSim` false becomes an `ATCWaypointType User` waypoint without `ICAO` (id = letters/digits of the ident, max 6: "BR-2197" → "BR2197") next to an anchor airport from `CareerService.NearestSimAirportAsync` (100 nm, else the job's other end): … → strip → anchor as destination, or anchor as departure → strip → …).
- **Airfields outside the sim's database**: OurAirports idents of small strips ("BR-2197") aren't known to MSFS, the GPS or SimBrief. Position logic never uses idents (departure check, arming, arrival all by distance), so such jobs fly normally. `CareerService.CheckAirportsInSimAsync` asks the sim (via `IAirportIlsLookup`, the market page does it in the background for accepted jobs) and stores the answer in `AirportFacilities` (a row with `HasIls` null = not in the sim); `Airport.InSim` carries it, `Airport.KnownToSim` falls back to "ident is a 3–4 letter/digit code". The market page hides the SimBrief steps for legs that aren't `KnownToSim`. Navigation: `Domain/World/Navigation` (`DirectTo`: initial true course via `GeoPosition.InitialCourseTo`, magnetic with variation, ETE, track offset; `DegreesMinutes` for GPS user waypoints, `Decimal` "-18.49150, -51.29880" for the copy button, since the MSFS world map/EFB search takes decimal pairs), shown by `Components/NavInfo.razor` on job cards (from the origin at cruise TAS) and on Live-Flug (from the live position at GS). Telemetry has `MagVar` (= `PLANE HEADING DEGREES TRUE` − `MAGNETIC`, so MSFS' MAGVAR sign never matters), `TrackTrueDeg` (`GPS GROUND TRUE TRACK`) and `HeadingTrueDeg`, null in old recordings. `missionMap.js` draws the 3 nm arrival ring for accepted jobs and a trail of live positions (restarted after a jump > 50 km).
- **Flight variety** (0.5): `Telemetry` also carries `BankDeg`/`PitchDeg`, `WindSpeedKt`/`WindDirectionDeg` (`AMBIENT WIND VELOCITY`/`DIRECTION`), `VisibilityM` (`AMBIENT VISIBILITY`, meters) and `ZuluSeconds`/`ZuluDayOfYear` (`ZULU TIME`, `ZULU DAY OF YEAR`), all null in old recordings and **not yet verified in the sim**. `Sim/Tracking/ComfortTracker` builds `Domain/Career/ComfortStats` from airborne samples (max and "sustained" bank/sink/G = held for 3 s/5 s/1 s, seconds of steep bank > 30°, sink > 3000 fpm, G outside 0.6–1.4) → `FlightSummary.Comfort` → `FlightResult.Comfort`. `Missions/Settlement/PassengerComfort.Rate` (only with passengers and stats) gives `ComfortRating` (G 30 %, bank 25 %, descent 20 %, landing 25 %); its `InFlight` part replaces `FlightScore.Smoothness`, `FlightSettlement.TipShare` pays 2–5 % from comfort 90, `PassengerComfort.Comments` picks up to three comments by `StableHash(contract id)` (stored as `FlightRecord.Comfort`/`PassengerComments`, not in `Notes`). Mission JSON: `handling` (`HandlingRule`: `maxGForce`/`maxBankDeg`/`maxSinkFpm` against the sustained values, `penalty` per exceeded limit, at most 2, `reason` patient/livestock/dangerous/fragile) and `timing` (`TimingRule`: `deadlineFactor`/`deadlineSlackHours` replace the generator's 1.5 × block + 2 h, `perMinuteEarly`/`maxEarlyBonus` pay on `Completed`). Landing conditions: `Telemetry.Conditions` (night = sun below −6° via `Domain/World/SolarPosition` from the sim's zulu time, visibility, crosswind against the heading via `Navigation.CrosswindKt`) is stored in `TouchdownReport.Conditions` → `FlightResult.LandingConditions`; `FlightSettlement.ConditionBonuses` pays 5 % each (night, visibility < 5 km, crosswind ≥ 10 kt) when the touchdown is within the type's `MaxTouchdownFpm`. Demand events: `Missions/Generation/DemandEvents.At(seed, gameTime, airport)` is regional (pure; `RegionOf(position)` = a cell of 1.5° latitude and the same distance in longitude, `StableHash(seed, "demand", ISO year, week, row, column)` against 50 ‰, the kind from a second hash; every non-military airport in the cell has the event) → `GenerationContext.Demand`: destination weight × 4 and pay × 1.25 (passenger kinds, categories airline/charter) or × 1.30 (relief supplies/harvest, cargo/bush), stored as `MissionContract.DemandEvent`; `CareerService.GetDemandEventsAsync` (one entry per region, named after its most important airport; passenger events in regions without a medium or large airport are left out) feeds the market banner and the map's golden region outlines, which are `interactive: false` so the jobs inside stay clickable. Fuel: `CostModel.FuelRegionFactor` (country table, else stable 0.90–1.15 per country, × 1.15 at idents that aren't ICAO-like) multiplies into `FuelPricePerKg`; the job card shows the price at origin and destination.
- **Clients** (0.6): `content/clients/*.json` → `Missions/Client` (`missionTypes`, optional `countries`, `chains` of `StoryChain` with `minStanding`, `completionStanding` and `StoryStep`s: `missionType`, fixed `destination` or `sizes`/`minNm`/`maxNm`, `cargoKind`, `bonus`; texts in `texts.de`), loaded into `GameContent.Clients`. Per career `Domain/Career/ClientStanding` (table `ClientStandings`, unique per career and client: `Standing` 0–100 from `ClientStandings.Start` 10, flights, running series, chain id/step, `CompletedChains`); `MissionContract.ClientId`/`ChainId`/`ChainStep`. `CareerService.Clients.cs`: `AssignClient` gives about 60 % of new offers a fitting client weighted by standing and multiplies all legs' pay by `ClientStandings.PayFactor` (+5 % per tier, silver 40, gold 70); `EnsureStoryOffersAsync` (only on real market searches, not with the tests' `rng`) puts each client's next unlocked step on the market for the first aircraft that can fly it (expires after `StoryOfferValidity` 30 days, skipped by the market cap); `SettleClientAsync` after each client flight applies `ClientStandings.Change` (+2/+3, late −3, diverted −5, crash −20; cancellation −5), counts the series (`StartSeriesAsync` from silver: `SeriesTarget` flights in 7 game days, 20 % bonus on their payouts, −5 when expired via `ExpireSeries`) and advances the chain; `SettlementInput.StoryBonus` pays the step's bonus, `SettlementResult.ClientNote` shows the standing change. Page `Clients.razor` (`/clients`).
- **Round trips** (0.6): mission types with `generator: "sightseeing"` (`SightseeingMissionGenerator`, registered next to the standard one; tests build their `MissionGeneratorRegistry` with both) and a `tour` rule (`TourRule`: 2–4 waypoints, `minAglFt`/`maxAglFt` band). Waypoints are the towns around (`Airport.City`, else the airport's name; one per town), flown in order of bearing; `DistanceNm` = tour length (`TourWaypoint.TourLengthNm`), so pay, deadline and fuel plan stay generic; origin = destination. Stored as `MissionContract.Waypoints` (`Domain/World/TourWaypoint` text, `WaypointList` ignored by EF). `FlightAutomation` hands them to the session (`IFlightSessionHost.SetWaypoints`, also after a resume; `FlightSession.SetWaypoints` re-checks recorded samples), a waypoint counts within 1.5 nm, airborne and inside the band; `FlightSummary.MissedWaypoints` → `FlightResult.MissedWaypoints`, and the settlement deducts payout × missed/total. Live-Flug shows the next waypoint (`FlightMonitorService.TourProgress`), the map draws `MissionMap.Route.Path`, `PlnExporter.Build(via:)` writes them as user waypoints.
- **Deliveries** (0.6): `AircraftProfile.DeliveryAirport` (shipped: C172 KIDP, C208 KICT, King Air KBEC, A20N LFBO, H145 EDMA). `AcquireAircraftAsync(..., DeliveryMode)` calls `ArrangeDeliveryAsync` (`CareerService.Delivery.cs`) for bought/leased aircraft when the delivery airport is known and not the home base: `Delivered` books `CostModel.Ferry` from there as `AircraftPurchase` and sets the ferry time as downtime; `PickUp` places the aircraft at the delivery airport with accepted contracts of type `delivery` (content, `weight: 0`, so `RequirementEvaluator.AvailableFor` never offers it; payout 0, no revenue line), one per leg of a `Delivery` package when `DeliveryStopsAsync` needs fuel stops (medium/large airports within 80 % of the range, nearest to home). `QuoteDeliveryAsync` feeds the fleet page's choice dialog.
- **In-flight events** (0.6): `Missions/Events/InFlightEvents` (pure): `Plan` gives about 10 % of jobs (`StableHash(contract id)`) a `PlannedEvent` that fits (medical emergency with passengers, destination change for single charter jobs, technical warning when a component is below `WearComponents.WarningLevel`), triggered at 30–60 % of the planned air time in climb/cruise/descent. `FlightAutomation.Events.cs` (`FollowEventsAsync`, called in the InProgress branch of `FollowAsync`) builds a `PendingInFlightEvent` (alternate = `NearestSuitable` other than the destination and nearer than it; new destination 20–80 nm from the old one, `ChangedPayout` +10 %; `PrecautionaryPayout` = share flown), raises `EventRaised` (system sound in `DepartureCoordinator`) and waits for `DecideEvent` up to 5 min (then declined). `CareerService.RecordEventAsync` stores `MissionContract.EventKind`/`EventAccepted`/`RevisedDestination` (accepted: payout and deadline adjusted). `EffectiveDestination` (= revised ?? destination) is what the settlement (`CompleteFlightAsync`), resume (`NearFlight`), GSX receipt matching, Live-Flug and the job card use; `FlightRecord.Destination` keeps the original. Settlement: medical diversion flown +2 reputation, ignored −3; technical warning ignored +3 condition loss; declined destination change −1 client standing. `AppSettings.InFlightEvents` (default on, Settings → Advanced) via `FlightAutomation.EventsEnabled`; debug mode has "Event now" buttons on Live-Flug (`TriggerEventNow`, also when switched off). Banner: `Components/Layout/InFlightEventPanel.razor` in `MainLayout`.
- **App**: singletons `FlightMonitorService` (owns the data source and the current `FlightSession`, thread-safe summaries), `GsxCoordinator` (polls GSX every 2 s; writes payload only on the ground before departure or once parked, see `GsxLoadSync.MayWrite` — never while the phase is still unknown after a restart; a departed job gets a `GsxLoadSync(departed: true)` that only follows deboarding, and a new job is queued while the previous one still deboards) and `DepartureCoordinator`, which ticks `Application/FlightAutomation` about once a second. There is no start button: an accepted job is armed (tracked, still editable) when the aircraft is on the ground at its origin, starts at liftoff unless the departure light (`Missions/Departure/DepartureCheck`) is red for position or type, records other red items as `DepartureIssues` (10 % payout each at settlement) and is settled automatically once parked. With several aircraft on jobs the loaded type decides (`AircraftProfile.MatchesSimTitle`): jobs of that type are armed first, and loading another aircraft at the stand switches to its job (not after a manual `Choose`). A job of another type is only armed when nothing matches, so its red type light explains why it won't start; `DepartureCoordinator` then sets no fuel, GSX target or arming time, and no start wear is read. GSX is pointed at a job only by `Armed`/`Resumed` (the market page just refreshes the tracked job's load sheet). With GSX in use (sync or costs on and GSX detected) the settlement waits for GSX deboarding (`FlightAutomation.GroundServices`/`Waiting`): `ReceiptGrace` (5 min) after it completed, since GSX writes the last receipts (crew bus) minutes later, after `DeboardingStartTimeout` (20 min) if it never starts (GSX shows `Completed` only briefly and then drops the deboarding state back to `Callable`, so `GsxDeboardingWatch` counts a deboarding seen running after departure as completed once it stops), at most 60 min, at once when an engine starts or the aircraft moves, or via „Jetzt abrechnen“ (`SettleNow`). Logging: `Application/Logging/FileLogger` (daily files in `logs\` next to the DB, 14 days) is the `ILoggerProvider` and `AppLog` the static entry point; `App` installs global exception handlers, `MainLayout` wraps pages in an `ErrorBoundary`, `Diagnostics` builds the "Diagnose kopieren" report. Fuel stays in the aircraft (`Career.PersistFuel`, default on): `CompleteFlightAsync` stores `FlightResult.FinalFuelKg` as `FleetAircraft.FuelKg`; `DepartureCoordinator` sets it in the sim once per job when it is armed on the ground (`MissionContract.FuelRestoredAtUtc` keeps a re-arm in the same sim connection from undoing later uplift; restored in an earlier connection, it is set again when the fuel differs and at most the crew is aboard, since the next job is often armed right after block-on and MSFS loads the flight later with its defaults); ending the flight in MSFS resets the aircraft to its defaults (Citation X: 50 % fuel) before the settlement, so `FlightSession` takes `FinalFuelKg`/burn at block-on (`_fuelAtBlockOn`) and `FlightAutomation` reads the end wear once `Arrived` (`_wearAtArrival`); a reset right after the restore (fuel and payload change at once, no GSX refuelling) is undone for `RestoreWatch` (60 s); the settlement then pays the uplift (`FlightSummary.FuelAtBlockOffKg` − stored fuel, `SettlementInput.FuelUpliftKg`) instead of the burn. Crash-safe flights: while a job is tracked `FlightMonitorService` writes a `FlightJournal` (`tracks\active-{id}.jsonl`); after a restart `FlightAutomation.TryResume` picks up `InProgress` jobs via `ResumeFlight` (journal replay, or `FlightSession.Resume` from the current state with times estimated from `FlightStartedAtUtc` and fuel from `MissionContract.FuelAtBlockOffKg`, stored at liftoff) and raises `Resumed`, which points GSX at the job again. Only with the job's type loaded and in the air or near the flight (last journal position, origin, destination); a job whose journal ends `Arrived`/`Crashed` while another aircraft is loaded is settled from the journal alone (`ResumeFlight(live: false)`: live telemetry ignored, no GSX wait, no sim wear, noted), any other stays `InProgress` without blocking other jobs. A job without start wear (resumed, or the read failed) reads it later in flight (retried every 30 s) and notes it in the settlement. Departure issues are stored on the contract at liftoff. App-wide (non-career) settings live in `AppSettings` (`appsettings.json` next to the DB). Its `DebugMode` (Einstellungen → Erweitert) shows the "Debug" menu group (Debug-Werkzeuge `/debug`, Beladungs-Spike; both wrapped in `DebugGate`) plus replay/test tracking and a phase override on Live-Flug (`FlightSession.ForcePhase`: sets milestone times, keeps the payload lock consistent, optional `FlightPhaseTracker.Frozen`; counted as `ManualPhaseChanges` and noted in the settlement) and free relocation in Fleet; the debug operations sit in `CareerService`'s "Debug tools" section (cash changes are booked as `LedgerCategory.Adjustment`, excluded from the monthly result like the starting capital). Menu: main pages, then the collapsible "Inhalte" group (profiles, mission types), "Debug", Einstellungen. The aircraft detail page `/fleet/{id}` (`AircraftDetail.razor`, data from `CareerService.GetAircraftDetailsAsync`) shows values, components with single/group repairs, economics from the aircraft's ledger entries, flights (links to `logbook?flight=`) and open jobs; „Standort ändern“ goes to `fleet?relocate=`. Shared fleet/ledger texts live in `Services/FleetTexts`. Pages derive from `CareerPageBase`, which reloads on `CareerService.Changed` and turns `CareerException` into snackbars. `MainLayout` shows `CareerSelect` instead of the app while no career is active. The mission map is Leaflet via `wwwroot/js/missionMap.js` (CDN, keyless tiles; CARTO now needs an API key).

## SimBrief facts (verified against a real OFP)

- `weights.cargo` is bags **plus** freight; the freight alone is `weights.freight_added`. Compare mission cargo with the freight.
- **`manualzfw` (verified 2026-11-01 with a real OFP):** sent together with `pax` and `cargo`, SimBrief keeps the passenger count and bags and plans exactly that ZFW; the freight becomes the balancing item (ZFW − its OEW − pax × pax weight − bags × bag weight; 891 instead of 2 500 kg when its A20N OEW was 1.7 t above ours). The dispatch link therefore always sends the load sheet's ZFW (`DispatchRequest.ZeroFuelWeightKg`, `SimBriefPayload.ZeroFuelWeightKg`), and `OfpExpectation.ManualZfw` makes `OfpValidator` check only passengers, dropped bags and the ZFW (20 kg tolerance; a larger difference means an OFP from an older link), not freight, payload or the airframe's pax/bag weights.
- SimBrief takes passenger and bag weight from the airframe (`pax_weight`/`bag_weight`, 175/50 lb by default) and adds one bag per passenger itself; the dispatch page ignores `acdata`, so neither can be set from the link (with `manualzfw` they only decide how SimBrief splits the payload). `SimBriefPayload.For(sheet, career.PassengerWeightKg, detailed)` builds the link values in two modes:
  - **Standard** (default, `Career.SimBriefDetailedLoad` off): `pax` = seated passengers, `cargo` = freight + cabin crew (omitted when 0). Offers copy SimBrief's model via `PassengerMassTable.ForCareer` and `GenerationContext.Masses`: children weigh as adults, every seated passenger has one `BagWeightKg` bag unless the type is `handOnly`/`none`. `OfpValidator` reports a pax/bag weight that differs from the career's and bags SimBrief dropped for MZFW/MTOW (`bag_count_actual` < `bag_count`).
  - **Detailed** (opt-in, Settings → Loading): `pax` = seated passengers, `cargo` = `SimPayload − pilots − pax × passenger weight` (bags, freight, infants, mass differences, cabin crew), so SimBrief's ZFW (OEW incl. pilots + payload) equals ours. Setting label "Varying bag weights per passenger"; with `manualzfw` the airframe's bag weight no longer matters. `GenerationContext.VaryBaggage` makes offers vary each bag 60–140 % around `BagWeightKg` with ~15 % of passengers without one; the drawn sum is frozen in `MissionContract.BaggageKg`.
- When the airframe's MZFW/MTOW limits the payload, SimBrief silently drops bags, then passengers (`pax_count_actual` < `pax_count`). `OfpValidator` reports this.
- `SimBriefPayload.ExpectedPayloadKg` is the payload the OFP would show without `manualzfw` (only checked when `ManualZfw` is off). GSX takes the passenger count from the OFP, which never contains crew (`GsxLoadSync.PassengerMismatch`).
- The loading screen in `wwwroot/index.html` runs before Blazor: `MainWindow` injects `window.skyLang` (`L.Language`) via `AddScriptToExecuteOnDocumentCreatedAsync`, and the page keeps its own English/German status lines (browser language as fallback).
- The sim only reports max gross weight, so profile drafts must estimate MZFW/MLW (`AircraftProfileEstimator`); MZFW = MTOW on a jet lets missions overload the aircraft.

## SimBrief aircraft types

- `SimBriefAircraftCatalog` loads SimBrief's public type list `https://www.simbrief.com/api/inputs.airframes.json` (no key, ~227 types) and caches the parsed types as `simbrief-types.json` next to the DB for 7 days (`SimBriefCatalogService`, offline falls back to the cache).
- Only each type's **default airframe** (`airframe_id: false`) is used: weights in `wgtunits` (LBS so far), `paxwgt`/`bagwgt` in lb. The list also embeds **other users' airframes** (user/pilot ids) — ignore them, never store them. 19 types have no default airframe; they only get the type-level `aircraft_mtow_kgs` and `aircraft_passengers`.
- `aircraft_speed` is "Mach 0.78" (jets) or "150 KIAS"; `CruiseKtas` approximates TAS (Mach × 573.6 kt; KIAS + 2 %/1000 ft at 70 % of the ceiling, max FL250). Takeoff/landing distances are in ft.
- `SimBriefProfileDraft.FromSimBrief` builds a complete profile without stations (`Loading = Manual`); `Merge` puts SimBrief's limits and performance into a sim draft and keeps the sim's empty weight, stations and title (warns when SimBrief's OEW differs by > 5 %).

## MSFS 2024 wear and tear (verified with the Citation X, 2026-10-30)

- SimVars from the SDK (`ModelBehaviorDefs/Asobo_EX1/Generic/Shared/Helpers/Helpers.xml`): `WEAR AND TEAR LEVEL:{id}` with component ids 0–49 (flaps 5–8, ailerons 9–12, elevator 13/14, rudder 19/20, alternator 28, battery 29, landing gear 35, brake 36, tire 37, piston engine 39, turbine 40, general 46 …), `WEAR AND TEAR CHECK PROGRESSION:{id}`, `REGULAR/RUNWAY/MUD/DUST/LEAKS DIRT PCT`, `BRAKE LEFT/RIGHT WEIGHT REMAINING`. The plain `…:{id}` index works in SimConnect data definitions (batch reads fine).
- `WEAR AND TEAR LEVEL` is the **remaining condition**: 1 = new, lower = worn (flaps 0.90, tire 0.977, gear 0.978 after use). Components the aircraft doesn't have read **0**, so 0 means "absent", not "broken".
- `WEAR AND TEAR LEVEL` is **read-only**: writing answers `DATA_ERROR` with the units number, percent over 100 and percent. Wear can be stored and shown, but not restored into the sim. `WEAR AND TEAR CHECK PROGRESSION` and the `… DIRT PCT` values are writable.
- `SCRATCHES DIRT PCT` doesn't exist (`NAME_UNRECOGNIZED`). Dirt starts collecting again right after it is set to 0.
- The "Beladungs-Spike" page (debug) reads them all and has a write test (`IAircraftLoader.WriteVariableAsync`).
- How SkyCareer uses it (`Domain/Aircraft/AircraftWear.cs`): since the sim can't be set, SkyCareer keeps its **own** component state (`FleetAircraft.ComponentWear`, text "id=level;…", missing = new) and only takes the sim's **change during a flight**. `FlightAutomation` reads `WearReader` via `IFlightSessionHost.ReadWearAsync` when the job is armed in Preflight (`MissionContract.SimWearAtStart`, once per job) and again before settling; `AircraftWear.Delta` ignores components that got better (repaired in the sim). The settlement adds `FleetEconomics.SimConditionLoss` (average component loss × 100 × `WearComponents.SimWearFactor`, a first estimate to tune) to the model's condition loss and notes the most worn groups; `CompleteFlightAsync` wears the components (not on rentals: the lessor maintains them, as with checks). `FleetAircraft.EffectiveCondition` (min of condition and worst component) drives the maintenance reserve; repairs add `FleetEconomics.ComponentRepairCost` (per component new price × `WearComponents.ComponentRepairShare` = group share / components in the group × wear, so a tire stays cheap and single, group and full repairs add up to the same); `CareerService.RepairComponentsAsync` repairs single components or groups with the longest `WearComponents.RepairDowntime` of the groups (tires/brakes 2 h, engine 24 h, else 6 h), never on rentals or while the aircraft is flying; repairs restore all components, scheduled checks +0.15. Below `WearComponents.WarningLevel` (70 %) `DepartureCheck` shows a yellow "Technik" item that never blocks or costs payout.

## GSX receipt facts (verified against real receipts)

- GSX Pro writes every bill as JSON plus a printable HTML to `%APPDATA%\Virtuali\GSX\Receipts\<Handling|Catering|Fuel|PassengerBus>\yyyyMMddTHHmmssZ_ICAO_TAIL.json` (`receiptId`, `icao`, `operator`, `title`, `items[]`, `taxes[]`, `total`). Amounts are text, local currency first plus a USD equivalent (`"£147.62 ~$ 196.50"`); euros are used as they are, everything else is converted from the USD part with GSX's own rate cache (`Couatl\Cache\fx-rates-v2.json`, base USD).
- The departure handling receipt (pushback) appears at liftoff, the fuel receipt right after refuelling. With GSX in use the settlement waits for deboarding, so its receipt normally belongs to the active job; a receipt at the active job's origin that is older than `MissionContract.ArmedAtUtc` goes to the previous flight that arrived there.
- With `Career.GsxCostsEnabled`, `GsxReceiptWatcher` (App) scans every 10 s and calls `CareerService.BookGsxReceiptsAsync`: receipts newer than `GsxCostsSinceUtc` go to the active job (at its origin/destination), else the last flight that arrived there, else an aircraft parked there; unmatched ones are retried. `GsxReceipts` (unique per career and `receiptId`) prevents double booking; the HTML is copied to `receipts\` next to the DB. `SettlementInput.ExternalGroundCosts` then drops the model's fuel, handling and catering lines, and the receipts are added to the flight's costs. `SKYCAREER_GSX_RECEIPTS` overrides the receipts folder for testing.

## Conventions and pitfalls

- Never put padding utility classes (`pa-4` etc., they are `!important`) on `MudMainContent`: its `padding-top` reserves the app bar height. Page padding lives on the inner `div` in `MainLayout`.
- BlazorWebView renders through `WebView2CompositionControl` (Direct3D image). Its recovery after a display change (MSFS full screen/resolution/HDR) only retries on `COMException`; a D3D9 `ArgumentException` left the UI black for good (WebView2 SDK 1.0.4258.31). `WebViewDisplayRecovery` catches it in `DispatcherUnhandledException` (no message box) and retries the private `GraphicsItemD3DImage.RecoverAfterDisplayChange` via reflection every second for up to 2 min; it logs a warning at start when the internals are gone after an SDK update.
- Telemetry and GSX events arrive on background threads; UI components must use `InvokeAsync(StateHasChanged)` and should throttle re-renders.
- Never block the UI thread on async cleanup (`OnExit` disposes services via `Task.Run` with a timeout); use `ConfigureAwait(false)` in library-side shutdown paths.
- Values that must stay identical across app restarts (e.g. the daily fuel price in `CostModel`) use a stable FNV hash, not `string.GetHashCode`.
- The values in `content/aircraft/*.json` are approximations. Station indices can be checked with the "Beladungs-Spike" page or the profile editor ("Stationen aus Sim übernehmen").
- Tests that need shipped content locate the repo root by searching upward for `SkyCareer.sln`.
