# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SkyCareer is a standalone Windows career add-on for Microsoft Flight Simulator 2024 (C# / .NET 10, WPF host with Blazor Hybrid UI and MudBlazor 9). UI text and user-facing messages are German; code, identifiers and comments are English.

## Commands

```bash
dotnet build SkyCareer.sln
dotnet test SkyCareer.sln
dotnet test tests/SkyCareer.Sim.Tests --filter "FullyQualifiedName~FlightTrackingTests.Touchdown_reports_rate_and_peak_g"
dotnet run --project src/SkyCareer.App
dotnet tool restore
dotnet ef migrations add <Name> --project src/SkyCareer.Data -o Migrations
```

- A running `SkyCareer.App.exe` locks `src/SkyCareer.App/bin/...`; close it first, or build the app elsewhere with `dotnet build src/SkyCareer.App -o <tempdir>`.
- The app migrates the database on startup. The DB lives at `%LOCALAPPDATA%\SkyCareer\skycareer.db` (override with the `SKYCAREER_DB` env var, e.g. to test the UI against a throwaway DB without touching the user's careers), user content in `Documents\SkyCareer\content`, exported flight plans in `Documents\SkyCareer\Flugplaene`.

## SimConnect is optional at build time

`SkyCareer.Sim.csproj` compiles the real `SimConnectSource` only when the MSFS 2024 SDK is found (via `SimConnectSdkDir`, the `MSFS2024_SDK` env var, or the default `C:\MSFS 2024 SDK`). It then defines `HAS_SIMCONNECT`, references the managed wrapper, copies the native `SimConnect.dll`, and targets x64. Without the SDK everything still builds and the app works in replay mode. Code outside `SimConnect/SimConnectSource.cs` must not reference SimConnect types; go through `FlightDataSourceFactory` and the interfaces in `Telemetry.cs` / `AircraftInspection.cs` (`IFlightDataSource`, `IAircraftLoader`, `IAircraftInspector`).

SimConnect facts verified against the live sim (keep them in mind when changing `SimConnectSource`):
- L:Vars can be read directly in data definitions, but **unknown L:Vars return 0 instead of an error**. Detect add-ons by plausible values, not by success (see `GsxState.Detected`).
- `DESIGN SPEED VC` already returns cruise **TAS** (525 kt for the Citation X).
- One-shot reads go through `RequestOnceAsync`, which maps SimConnect exceptions back to the request by packet id. Batch reads use a fixed 16-double struct (`ReadVariablesAsync`), padded with dummy L:Vars.
- Optional variables (`ReadDesignAsync`) sit in a separate request so a missing variable doesn't break the whole snapshot.
- Airport facility data (`ReadAirportAsync`): ILS is detected from **approaches of type 4 (ILS)**. The runway `PRIMARY/SECONDARY_ILS_ICAO` fields are empty at some airports (LSZH) and only serve as extra info. Read char[8] idents as byte arrays (string marshaling produced garbage). Unknown idents answer with an exception and no end record. Results are cached in the `AirportFacilities` table; OurAirports has no ILS data (`navaids.csv` only covers VOR/NDB/DME/TACAN).

## Architecture

Dependency direction: `Domain` ← `Sim`, `Missions`, `Data`, `Integrations.*` ← `Application` ← `App`. `Domain` has no external dependencies.

- **Domain**: units (`Mass` in kg, SimConnect pounds converted at the edge; `Money` as decimal), aircraft profiles, load planning (`LoadSheetBuilder`, `FuelPlanner`, `LoadVerifier`), the finance cost model, career entities (`Career`, `FleetAircraft`, `MissionContract`, `FlightRecord`, `LedgerEntry`), and the simulator-independent `FlightResult`.
  - Crew convention: `OperatingEmptyKg` equals the sim's EMPTY WEIGHT. Crew is loaded into crew stations on top, unless `CrewIncludedInEmptyWeight`. `LoadSheet.SimPayload` (payload + crew) is what the sim should report. Crew mass and crew costs use `AircraftProfile.Pilots` = max(`CrewCount`, `MinimumPilots`): two pilots for jets, MTOW > 5.7 t or > 9 seats unless tagged `single_pilot`. Pilots count `CrewMassKg` (default 85 kg), cabin crew `CabinCrewMassKg` (default 75 kg, EASA standard masses); with `Career.SimBriefDetailedLoad` the crew goes to SimBrief as passengers (see SimBrief facts), otherwise SimBrief doesn't see it.
- **Sim**: `FlightSession` combines `FlightPhaseTracker` (phase state machine with hysteresis, touchdown/bounce detection) and `IntegrityMonitor` (slew, sim rate, refuelling in flight, payload change, teleport, aircraft change). Payload is locked when the takeoff roll starts (released again after a rejected takeoff) and only checked from `TakeoffRoll` to `Approach` (unloading after landing is fine). After an app restart `FlightSession.ContinueAfterRestart` (journal replay) bridges a gap > 30 s without judging it: a different payload becomes the new lock (noted), a landing in the gap continues on the ground via `FlightPhaseTracker.Resume` without a touchdown rating. Violations never void a job: `FlightSettlement.ViolationPenalties` deducts per kind (slew/teleport/aircraft change 20 %, refuelling in flight 15 %, payload change 10 %, capped at 20 % of the payout), −1 reputation per kind and 20 safety score points; time acceleration is only noted (no payout, score or reputation cost). `FlightOutcome.Failed` only remains for old records. `ReplaySource` and `FlightLogFile` (JSON Lines) make all tracking testable without MSFS; tests build telemetry with `SyntheticFlight`.
- **Missions**: data-driven content. `ContentLoader` layers content roots (a later root overrides by id). `ContentStore` holds the current `GameContent` (shipped `content/` plus the user folder) and reloads after edits. Mission types are JSON (`content/missions`); the `RequirementEvaluator` matches them to aircraft via tags/seats/cargo/surfaces/range. `IMissionGenerator` implementations are selected by the mission type's `generator` name. `StandardMissionGenerator` only offers jobs whose load sheet fits the limits, weights destinations log-normally around 45 % of the aircraft's range (divided by distance^1.5 so the many far-away airports don't crowd out medium trips), and honours an optional `MissionSearch` (also used as the market list filter). `Settlement/FlightSettlement` is a pure function: contract + `FlightResult` → outcome, score, ledger lines, wear, reputation.
- **Data**: one SQLite DB for all careers (scoped by `CareerId`, FK cascade) plus shared airport data from OurAirports (`OurAirportsImporter`). At import each airport is matched to the city it serves (`GeoNamesCities`, GeoNames cities15000: population fading with distance, capital flag); mission types weight destinations by that via `destinations.cityWeight` and can demand a per-search `minCapitalShare` (enforced in `SearchMarketAsync` like `minLargeShare`, via `RequireCapital`); `distanceInfluence` (< 1) damps the preferred-distance weighting so city importance wins. Military fields are flagged by name at import (`OurAirportsImporter.IsMilitaryField`, joint-use fields with scheduled service stay civil) and only offered to profiles tagged `military`. By convention, enums and `decimal` are stored as strings, so sums and money sorting happen in memory.
- **Application**: `CareerService` is the only place career state changes (fleet incl. relocation by paid ferry flight via `CostModel.Ferry` or free move, market, accept/start/complete flight, wait, monthly fixed costs). Mission pay = rule terms + `pay.hourlyRateFactor` × `FleetEconomics.HourlyRate` (rent + fuel per block hour), so payouts follow the aircraft class. Each method uses its own `DbContext` from `IDbContextFactory` and raises `Changed`. Game time is flight-based: it only advances through flights (+ turnaround) and `WaitAsync`.
- **Integrations**: `SimBrief` (dispatch link + OFP fetch/validation, no API key), `Gsx` (reads `FSDT_GSX_*` L:Vars; `GsxLoadSync` turns GSX boarding/deboarding progress into scaled station loads; `GsxReceiptReader` reads GSX Pro's receipts), `BeyondAtc` (BeyondATC has no API; `PlnExporter` writes MSFS `.pln` files it can import).
- **App**: singletons `FlightMonitorService` (owns the data source and the current `FlightSession`, thread-safe summaries), `GsxCoordinator` (polls GSX every 2 s; writes payload only on the ground before departure or once parked, see `GsxLoadSync.MayWrite` — never while the phase is still unknown after a restart; a departed job gets a `GsxLoadSync(departed: true)` that only follows deboarding, and a new job is queued while the previous one still deboards) and `DepartureCoordinator`, which ticks `Application/FlightAutomation` about once a second. There is no start button: an accepted job is armed (tracked, still editable) when the aircraft is on the ground at its origin, starts at liftoff unless the departure light (`Missions/Departure/DepartureCheck`) is red for position or type, records other red items as `DepartureIssues` (10 % payout each at settlement) and is settled automatically once parked. With GSX in use (sync or costs on and GSX detected) the settlement waits for GSX deboarding (`FlightAutomation.GroundServices`/`Waiting`): 15 s after it completed (receipt grace), after `DeboardingStartTimeout` (20 min) if it never starts, at most 60 min, at once when an engine starts or the aircraft moves, or via „Jetzt abrechnen“ (`SettleNow`). Logging: `Application/Logging/FileLogger` (daily files in `logs\` next to the DB, 14 days) is the `ILoggerProvider` and `AppLog` the static entry point; `App` installs global exception handlers, `MainLayout` wraps pages in an `ErrorBoundary`, `Diagnostics` builds the "Diagnose kopieren" report. Fuel stays in the aircraft (`Career.PersistFuel`, default on): `CompleteFlightAsync` stores `FlightResult.FinalFuelKg` as `FleetAircraft.FuelKg`; `DepartureCoordinator` sets it in the sim once per job when it is armed on the ground (`MissionContract.FuelRestoredAtUtc` keeps a re-arm from undoing later uplift); the settlement then pays the uplift (`FlightSummary.FuelAtBlockOffKg` − stored fuel, `SettlementInput.FuelUpliftKg`) instead of the burn. Crash-safe flights: while a job is tracked `FlightMonitorService` writes a `FlightJournal` (`tracks\active-{id}.jsonl`); after a restart `FlightAutomation.TryResume` picks up `InProgress` jobs via `ResumeFlight` (journal replay, or `FlightSession.Resume` from the current state with times estimated from `FlightStartedAtUtc` and fuel from `MissionContract.FuelAtBlockOffKg`, stored at liftoff) and raises `Resumed`, which points GSX at the job again. A job without start wear (resumed, or the read failed) reads it later in flight (retried every 30 s) and notes it in the settlement. Departure issues are stored on the contract at liftoff. App-wide (non-career) settings live in `AppSettings` (`appsettings.json` next to the DB). Its `DebugMode` (Einstellungen → Erweitert) shows the "Debug" menu group (Debug-Werkzeuge `/debug`, Beladungs-Spike; both wrapped in `DebugGate`) plus replay/test tracking and a phase override on Live-Flug (`FlightSession.ForcePhase`: sets milestone times, keeps the payload lock consistent, optional `FlightPhaseTracker.Frozen`; counted as `ManualPhaseChanges` and noted in the settlement) and free relocation in Fleet; the debug operations sit in `CareerService`'s "Debug tools" section (cash changes are booked as `LedgerCategory.Adjustment`, excluded from the monthly result like the starting capital). Menu: main pages, then the collapsible "Inhalte" group (profiles, mission types), "Debug", Einstellungen. The aircraft detail page `/fleet/{id}` (`AircraftDetail.razor`, data from `CareerService.GetAircraftDetailsAsync`) shows values, components with single/group repairs, economics from the aircraft's ledger entries, flights (links to `logbook?flight=`) and open jobs; „Standort ändern“ goes to `fleet?relocate=`. Shared fleet/ledger texts live in `Services/FleetTexts`. Pages derive from `CareerPageBase`, which reloads on `CareerService.Changed` and turns `CareerException` into snackbars. `MainLayout` shows `CareerSelect` instead of the app while no career is active. The mission map is Leaflet via `wwwroot/js/missionMap.js` (CDN, keyless tiles; CARTO now needs an API key).

## SimBrief facts (verified against a real OFP)

- `weights.cargo` is bags **plus** freight; the freight alone is `weights.freight_added`. Compare mission cargo with the freight.
- SimBrief takes passenger and bag weight from the airframe (`pax_weight`/`bag_weight`, 175/50 lb by default) and adds one bag per passenger itself; the dispatch page ignores `acdata`, so neither can be set from the link. `SimBriefPayload.For(sheet, career.PassengerWeightKg, detailed)` builds the link values in two modes:
  - **Standard** (default, `Career.SimBriefDetailedLoad` off): `pax` = seated passengers, `cargo` = freight (omitted when 0). Offers copy SimBrief's model via `PassengerMassTable.ForCareer` and `GenerationContext.Masses`: children weigh as adults, every seated passenger has one `BagWeightKg` bag unless the type is `handOnly`/`none`. `OfpValidator` reports a pax/bag weight that differs from the career's and bags SimBrief dropped for MZFW/MTOW (`bag_count_actual` < `bag_count`).
  - **Detailed** (opt-in, Einstellungen → Beladung): `pax` = seated passengers + crew (`Pilots + CabinCrewCount`, none if `CrewIncludedInEmptyWeight`), `cargo` = `SimPayload − pax × passenger weight` (bags, freight, infants, crew standard masses vs passenger weight), so SimBrief's ZFW equals ours. Needs **bag weight 0** in the airframe (`OfpExpectation.BagsAsFreight` makes `OfpValidator` report a bag weight > 0). `GenerationContext.VaryBaggage` makes offers vary each bag 60–140 % around `BagWeightKg` with ~15 % of passengers without one; the drawn sum is frozen in `MissionContract.BaggageKg`.
- When the airframe's MZFW/MTOW limits the payload, SimBrief silently drops bags, then passengers (`pax_count_actual` < `pax_count`). `OfpValidator` reports this.
- GSX takes the passenger count from the OFP and therefore boards the crew too in detailed mode; `GsxLoadSync.PassengerMismatch` accepts that.
- The sim only reports max gross weight, so profile drafts must estimate MZFW/MLW (`AircraftProfileEstimator`); MZFW = MTOW on a jet lets missions overload the aircraft.

## SimBrief aircraft types

- `SimBriefAircraftCatalog` loads SimBrief's public type list `https://www.simbrief.com/api/inputs.airframes.json` (no key, ~227 types) and caches the parsed types as `simbrief-types.json` next to the DB for 7 days (`SimBriefCatalogService`, offline falls back to the cache).
- Only each type's **default airframe** (`airframe_id: false`) is used: weights in `wgtunits` (LBS so far), `paxwgt`/`bagwgt` in lb. The list also embeds **other users' airframes** (user/pilot ids) — ignore them, never store them. 19 types have no default airframe; they only get the type-level `aircraft_mtow_kgs` and `aircraft_passengers`.
- `aircraft_speed` is "Mach 0.78" (jets) or "150 KIAS"; `CruiseKtas` approximates TAS (Mach × 573.6 kt; KIAS + 2 %/1000 ft at 70 % of the ceiling, max FL250). Takeoff/landing distances are in ft.
- `SimBriefProfileDraft.FromSimBrief` builds a complete profile without stations (`Loading = Manual`); `Merge` puts SimBrief's limits and performance into a sim draft and keeps the sim's empty weight, stations and title (warns when SimBrief's OEW differs by > 5 %).

## MSFS 2024 wear and tear (verified with the Citation X, 2026-10-30)

- SimVars from the SDK (`ModelBehaviorDefs/Asobo_EX1/Generic/Shared/Helpers/Helpers.xml`): `WEAR AND TEAR LEVEL:{id}` with component ids 0–49 (flaps 5–8, ailerons 9–12, elevator 13/14, rudder 19/20, alternator 28, battery 29, landing gear 35, brake 36, tire 37, piston engine 39, turbine 40, general 46 …), `WEAR AND TEAR CHECK PROGRESSION:{id}`, `REGULAR/RUNWAY/MUD/DUST/LEAKS DIRT PCT`, `BRAKE LEFT/RIGHT WEIGHT REMAINING`. The plain `…:{id}` index works in SimConnect data definitions (batch reads fine).
- `WEAR AND TEAR LEVEL` is the **remaining condition**: 1 = new, lower = worn (flaps 0.90, tire 0.977, gear 0.978 after use). Components the aircraft doesn't have read **0**, so 0 means "absent", not "broken".
- `WEAR AND TEAR LEVEL` is **read-only**: writing answers `DATA_ERROR` with the units number, percent over 100 and percent. Wear can be stored and shown, but not restored into the sim. `WEAR AND TEAR CHECK PROGRESSION` and the `… DIRT PCT` values are writable.
- `SCRATCHES DIRT PCT` doesn't exist (`NAME_UNRECOGNIZED`). Dirt starts collecting again right after it is set to 0.
- The "Beladungs-Spike" page (debug) reads them all and has a write test (`IAircraftLoader.WriteVariableAsync`).
- How SkyCareer uses it (`Domain/Aircraft/AircraftWear.cs`): since the sim can't be set, SkyCareer keeps its **own** component state (`FleetAircraft.ComponentWear`, text "id=level;…", missing = new) and only takes the sim's **change during a flight**. `FlightAutomation` reads `WearReader` via `IFlightSessionHost.ReadWearAsync` when the job is armed in Preflight (`MissionContract.SimWearAtStart`, once per job) and again before settling; `AircraftWear.Delta` ignores components that got better (repaired in the sim). The settlement adds `FleetEconomics.SimConditionLoss` (average component loss × 100 × `WearComponents.SimWearFactor`, a first estimate to tune) to the model's condition loss and notes the most worn groups; `CompleteFlightAsync` wears the components (not on rentals: the lessor maintains them, as with checks). `FleetAircraft.EffectiveCondition` (min of condition and worst component) drives the maintenance reserve; repairs add `FleetEconomics.ComponentRepairCost` (per component new price × `WearComponents.ComponentRepairShare` = group share / components in the group × wear, so a tire stays cheap and single, group and full repairs add up to the same); `CareerService.RepairComponentsAsync` repairs single components or groups with the longest `WearComponents.RepairDowntime` of the groups (tires/brakes 2 h, engine 24 h, else 6 h), never on rentals or while the aircraft is flying; repairs restore all components, scheduled checks +0.15. Below `WearComponents.WarningLevel` (70 %) `DepartureCheck` shows a yellow "Technik" item that never blocks or costs payout.

## GSX receipt facts (verified against real receipts)

- GSX Pro writes every bill as JSON plus a printable HTML to `%APPDATA%\Virtuali\GSX\Receipts\<Handling|Catering|Fuel|PassengerBus>\yyyyMMddTHHmmssZ_ICAO_TAIL.json` (`receiptId`, `icao`, `operator`, `title`, `items[]`, `taxes[]`, `total`). Amounts are text, local currency first plus a USD equivalent (`"£147.62 ~$ 196.50"`); euros are used as they are, everything else is converted from the USD part with GSX's own rate cache (`Couatl\Cache\fx-rates-v2.json`, base USD).
- The departure handling receipt (pushback) appears at liftoff, the fuel receipt right after refuelling. With GSX in use the settlement waits for deboarding, so its receipt normally belongs to the active job; a receipt at the active job's origin that is older than `MissionContract.ArmedAtUtc` goes to the previous flight that arrived there.
- With `Career.GsxCostsEnabled`, `GsxReceiptWatcher` (App) scans every 10 s and calls `CareerService.BookGsxReceiptsAsync`: receipts newer than `GsxCostsSinceUtc` go to the active job (at its origin/destination), else the last flight that arrived there, else an aircraft parked there; unmatched ones are retried. `GsxReceipts` (unique per career and `receiptId`) prevents double booking; the HTML is copied to `receipts\` next to the DB. `SettlementInput.ExternalGroundCosts` then drops the model's fuel, handling and catering lines, and the receipts are added to the flight's costs. `SKYCAREER_GSX_RECEIPTS` overrides the receipts folder for testing.

## Releases & updates

- Velopack + public GitHub Releases. `tools/release.ps1 -Version x.y.z` tests, publishes (framework-dependent, win-x64), checks that `SimConnect.dll` and `content/` are included, packs (`vpk` local tool, delta against the last release) and uploads with the token from `SKYCAREER_GH_TOKEN`. `-PackOnly` builds the installer locally only.
- Version and repo URL live in `Directory.Build.props` (`Version`, `SkyCareerRepoUrl`); the app reads the URL via `AssemblyMetadata("RepoUrl")`.
- `Program.Main` (`StartupObject`) must call `VelopackApp.Build().Run()` before WPF starts.
- Pack ID is `SkyCareerApp`, **not** `SkyCareer`: Velopack installs to `%LOCALAPPDATA%\<packId>` and deletes it on uninstall, and the careers DB lives in `%LOCALAPPDATA%\SkyCareer`.
- `UpdateService` is disabled unless installed by Velopack (dev builds show "Entwicklungsversion"). It checks 10 s after start and every 6 h, downloads in the background, refuses to restart during a tracked flight (`CanRestartNow`) and applies a downloaded update on exit (`App.OnExit` → `ApplyOnExit`).

## Conventions and pitfalls

- Never put padding utility classes (`pa-4` etc., they are `!important`) on `MudMainContent`: its `padding-top` reserves the app bar height. Page padding lives on the inner `div` in `MainLayout`.
- Telemetry and GSX events arrive on background threads; UI components must use `InvokeAsync(StateHasChanged)` and should throttle re-renders.
- Never block the UI thread on async cleanup (`OnExit` disposes services via `Task.Run` with a timeout); use `ConfigureAwait(false)` in library-side shutdown paths.
- Values that must stay identical across app restarts (e.g. the daily fuel price in `CostModel`) use a stable FNV hash, not `string.GetHashCode`.
- The values in `content/aircraft/*.json` are approximations. Station indices can be checked with the "Beladungs-Spike" page or the profile editor ("Stationen aus Sim übernehmen").
- Tests that need shipped content locate the repo root by searching upward for `SkyCareer.sln`.
